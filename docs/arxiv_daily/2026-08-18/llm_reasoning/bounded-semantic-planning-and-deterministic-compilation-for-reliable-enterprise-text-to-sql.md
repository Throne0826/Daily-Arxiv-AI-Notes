<span class="paper-mini-label">先用一句话判断</span>

本文研究一种语义路径编译架构，使语言模型只负责从受治理的语义选项中理解问题和选择对象，而由确定性程序负责关系路径、角色绑定、聚合粒度及 SQL 生成，以提高企业级 Text-to-SQL 的可靠性。

**不用术语来说**：企业用户提出的问题通常不是简单地把文字翻译成 SQL：同一个业务概念可能对应多条关系路径，某些关系还带有角色含义，连接和聚合顺序也会影响结果。语言模型即使生成了能够执行的 SQL，也可能使用了错误的业务关系并得到看似合理的数字。因此，问题不只是“SQL 能否运行”，而是“查询是否真正表达了用户想问的业务含义”。

</div>

<div class="paper-quickread__side" markdown="1">

<span class="paper-mini-label">核心贡献</span>

- 提出语义路径编译（SPC）系统，将随机性限制在问题理解、术语落地和受治理选项选择阶段；模型不能直接编写表名、列名、连接条件或 SQL 片段，后续由确定性引擎完成路径解析、角色处理、粒度降低、SQL AST 构造和治理检查。
- 在 ACME 保险基准的配对评测中，比较 SPC 与直接 DDL-to-SQL 生成，考察重复运行下的语义正确性、错误但可执行结果以及严格等价敏感性；论文将结果定位为受治理工作负载上的端到端系统证据，而非“仅由编译器导致提升”的因果证明。

</div>

## 研究背景

<div class="paper-section-deck" markdown="1">

企业文本到 SQL 的目标，是把自然语言业务问题转换为可在关系数据库上执行且语义正确的查询。这里的难点不只在于生成语法合法的 SQL，还在于确定业务概念对应的关系路径、区分同一实体在不同关系中的角色，并在连接和聚合时保持正确的数据粒度；这些错误往往仍会产生可执行 SQL 和看似合理的数值，因此，仅检查语法、执行成功或单个数据库快照上的结果一致性并不足以保证正确。本文研究语义路径编译（Semantic Path Compilation, SPC）：让语言模型只负责理解问题并从当前问题对应的有限、受治理选项中作出选择，而由确定性程序负责解析关系路径、绑定角色、降低粒度、构造 SQL 抽象语法树并执行治理检查。

</div>

<p class="paper-minor-label">小白先知道</p>

<div class="concept-list" markdown="1">

<div class="concept-item" markdown="1">

**语义层与受治理本体**

语义层用业务概念、关系、角色、指标、属性和基数等元数据描述数据库允许表达的业务含义，并通过物理映射把这些元素连接到表、列、键和谓词。所谓“受治理”，是指可用概念和关系由系统预先定义和审查，而不是由语言模型临时创造。

</div>
<div class="concept-item" markdown="1">

**数据粒度与可汇总性**

数据粒度表示一行数据对应的对象层级，例如“一位客户”“一张保单”或“一次理赔”；连接一对多关系后直接聚合，可能重复计算原有数值。可汇总性描述某个指标能否沿给定维度和关系安全聚合，是避免扇出和错误总计的关键条件。

</div>
<div class="concept-item" markdown="1">

**确定性编译与随机边界**

确定性编译指在已接受的语义计划、本体、物理映射和编译器版本固定后，最终 SQL 由代码按规则唯一构造。随机边界表示语言模型的不确定性被限制在语言落地和受治理选项选择阶段，模型不能直接编写表名、列名、连接条件、角色谓词或 SQL 片段。

</div>

</div>

<div class="paper-focus" markdown="1">

**论文具体研究什么**

输入是一个自然语言业务问题，以及受治理本体 $O$、物理映射 $M$ 和数据库快照 $D$。多轮语言模型规划器可以引用问题中的原文片段、选择查询主体，并从类型化检索工具返回的、针对当前问题的有限候选中提交语义标识符和路径不透明句柄；它不能直接访问或创作数据库结构与 SQL。确定性引擎随后解析绑定与规范路径，复核计划的完整性和可接受性，处理关系角色及聚合粒度，构造 SQL 抽象语法树，并检查已知治理违规；只有复核通过且不存在阻断性违规时才释放 SQL，否则拒绝请求，最多允许一次仅携带拒绝原因的全新重试。本文所处场景强调企业模式中的角色敏感关系和多重性风险，并将“正确回答、拒绝、错误但可执行”区分为不同结果；数据库快照可用于字面量探测和执行，但不决定某条关系路径是否合规。

</div>

**直接相关的工作**

- **ATHENA / ATHENA++**: ATHENA 先把自然语言映射为本体查询语言，再将本体层查询确定性翻译为 SQL；ATHENA++进一步支持嵌套与聚合查询。它们说明本体层解释、语义图路径构造和确定性数据库翻译已有先例，而本文关注的是更严格的系统权限边界：规划器只能选择当前问题返回的受治理词汇和路径句柄。
- **MetricFlow**: MetricFlow 通过已建模实体组合连接，并在语义层覆盖范围内确定性生成 SQL，与 SPC 都把部分关系推理和 SQL 构造移出语言模型。本文进一步限制模型不得编写连接、聚合结构或 SQL，并以计划复核、角色绑定、粒度处理和治理检查组成端到端发布或拒绝流程。

## 研究动机

<div class="paper-section-deck" markdown="1">

企业级 Text-to-SQL 的风险来自语义决策错误，而不只是语法错误。系统需要判断用户问题对应的业务概念，选择正确的关系路径和关系角色，并保持连接与聚合所需的粒度。若这些决策错误，生成的 SQL 仍可能通过数据库解析、成功执行，并返回符合表面直觉的数字；这会使传统的解析有效性或单一数据库实例上的结果吻合无法充分保障查询可靠性。实际需求因此是建立一种能够约束高风险关系决策、同时保留自然语言理解能力的完整查询生成流程。

</div>

<div class="paper-two-column" markdown="1">

<div markdown="1">

<span class="paper-mini-label">过去怎么做</span>

- **直接 DDL-to-SQL 生成**：语言模型读取数据库 DDL，即表、列和约束等结构描述，然后直接把自然语言问题转换为完整 SQL。它把业务解释、关系路径选择、角色条件、聚合结构和 SQL 编写集中交给同一个随机生成过程，流程灵活，但模型也可以直接授权自己决定底层关系结构。
- **语义层或本体驱动方法**：语义层方法先用受治理的实体、关系、指标和属性表达业务含义，再根据这些语义对象生成查询；MetricFlow 等系统可依据建模实体组合连接并确定性地产生 SQL，ATHENA 和 ATHENA++ 等本体中介方法则先构造本体层解释，再翻译到 SQL。这类方法说明语义图遍历和确定性翻译能够降低部分结构错误，但其覆盖范围取决于预先建模的语义范围。

</div>

<div markdown="1">

<span class="paper-mini-label">问题出在哪里</span>

- 直接生成方法同时承担语义解释和关系结构编写，模型可能选择错误的关系角色、连接路径或聚合粒度；其结果可能是“错误但可执行”的 SQL，解析成功因而不能代表业务语义正确。
- 已有语义层或本体方法通常把较多决策移入治理元数据，但尚未直接回答一种更窄的系统设计问题：当语言模型仍负责理解问题和选择有限语义候选，而完全不能编写关系结构时，重复运行下的可靠性会如何变化。换言之，语义治理、模型选择和确定性编译三者的边界及其端到端效果仍缺少针对该工作负载的明确评估。

</div>

</div>

<div class="motivation-core" markdown="1">

<div markdown="1"><span>研究空白</span>

尚未解决的空白是如何划分随机模型与确定性程序的职责，使模型能够处理自然语言中的业务表达，却不能越权决定表、列、连接谓词、角色谓词、聚合结构或 SQL。论文进一步需要检验：由有限的、问题相关的受治理语义选项驱动的模型计划，交给确定性引擎编译后，是否能在保持问题覆盖率的同时减少语义错误和运行结果偶合。

</div>
<div markdown="1"><span>核心问题</span>

当语言模型只被允许完成问题中的短语落地、主体选择和受治理语义标识选择，而关系路径解析、角色绑定、粒度处理、SQL 构造及已知治理条件检查全部由确定性引擎完成时，这种 SPC 架构是否能相较于直接 DDL-to-SQL 生成，在企业级数据库上提高重复运行的语义可靠性，并减少错误但可执行的查询？

</div>
<div markdown="1"><span>作者直觉</span>

核心直觉是把最难审计、且一旦出错就会产生可信假数字的结构性决定，从随机文本生成中移出。模型面对的不是整个数据库中任意可组合的表和列，而是工具返回的有限候选，并提交不可拆解、不可自行组合的路径标识；程序随后依据受治理本体和物理映射解析这些标识，统一决定连接、角色、粒度和 SQL 结构。这样模型仍能利用语言能力识别用户意图，但不能用一次看似合理的文字续写绕过业务规则；若计划不完整、路径不可接受或检查失败，系统可以拒绝发布 SQL，而不是把不确定答案直接交给数据库执行。

</div>

</div>

## 研究方法

<div class="paper-section-deck" markdown="1">

该系统是一种受治理的文本到 SQL 编译流程，输入是自然语言问题、由语义本体与物理映射共同构成的企业语义模型，以及数据库中的可验证数据。系统先由规划代理从问题中提取并绑定受治理的概念、指标、属性、字面量和候选路径，再由确定性引擎检查语义完整性，最后将被接受的语义计划编译为完整 SQL。其核心边界是：模型只能在动态检索出的有限候选项中进行选择，不能自由发明表、列、连接路径或角色条件；关系实现、角色谓词、分组和粒度转换由引擎确定性完成。这样做的直观含义是，模型负责回答“问题要什么、在允许的选项中选哪条路”，编译器负责回答“这些选择应如何准确翻译成 SQL”。

</div>

<p class="paper-minor-label">关键流程</p>

<div class="method-steps" markdown="1">

<div class="method-step" markdown="1">

<div class="method-step__body" markdown="1">

#### 1. 加载并验证受治理语义模型

加载器合并两类文件，并依据八项验证规则执行失败即停止的校验，确保每个可编译的语义对象具有足够的物理绑定。关系边显式记录端点、业务角色、基数、两个方向的扇出分类及其证据；指标则区分叶指标和由叶指标组合而成的复合指标。

<div class="method-step__io" markdown="1">

**输入**：语义文件与物理映射文件。语义文件描述概念、业务角色、关系边、指标及其聚合定义；物理映射文件将概念和关系绑定到表、键列、标记表和连接谓词。<br>
**输出**：可供解析和编译的受治理语义图及其物理映射；若模型存在未绑定或不一致内容，则不会进入编译阶段。

</div>

**直观理解**：这一步相当于先制作并检查一份企业数据字典。它把“政策持有人”和“销售代理人”作为不同业务关系保留下来，避免系统把两个含义不同的角色误当成同一种连接。

</div>

</div>
<div class="method-step" markdown="1">

<div class="method-step__body" markdown="1">

#### 2. 从问题中抽取并确定性绑定语义对象

解析器将问题片段绑定到受治理的概念、指标、属性、期间和字面量，并显式报告歧义或失败；它不要求模型自行构造关系路径。以示例问题为例，系统将“policy”绑定为 Policy，将“total premiums”和“total loss”绑定为相应指标，将“agent”“policy holder”和“policy number”绑定为角色概念及属性。

<div class="method-step__io" markdown="1">

**输入**：自然语言问题，以及规划代理提交的由问题原文片段组成的分解结果，包括 subjects、quantities、attributes 和 literals。<br>
**输出**：语义绑定集合，包括已识别的主体、指标、属性、字面量及后续路径搜索所需的目标对象。

</div>

**直观理解**：模型先把问题中的词语贴到目录中的正式名称上，而不是直接写 SQL。例如，它只能从目录里选择“保单”“销售代理人”和“总损失”等对象；如果一个词有多个解释，系统会把问题暴露出来，而不是静默猜测。

</div>

</div>
<div class="method-step" markdown="1">

<div class="method-step__body" markdown="1">

#### 3. 确定性检索并暴露候选路径

图枚举器依据治理约束、业务角色、支持范围和跳数上限，以确定性方式枚举所有合规路线，并将路线表示为不透明的路径句柄。数据库探针只用于字面量落地和诊断性扇出标注；观测到的多重性不会覆盖作者声明的基数，也不会自行使某条路径获得可用资格。

<div class="method-step__io" markdown="1">

**输入**：已绑定的语义对象、受治理语义图、物理映射和跳数上限。<br>
**输出**：每个必需目标对应的可接受候选路线及其路径句柄，供规划代理进行有限选择。

</div>

**直观理解**：系统先替模型找好所有合法道路，再让模型从这些道路中选一条。模型看到的是“路线选项”，而不是可以任意拼接的表连接序列，因此不能临时发明一条看似合理但未经治理的路径。

</div>

</div>
<div class="method-step" markdown="1">

<div class="method-step__body" markdown="1">

#### 4. 受限规划、独立审查与计划提交

多轮规划代理在固定类型工作流中行动，每一轮只能调用一次检索或审查工具，或者提交结构化计划。引擎动态生成 submit_plan 的 JSON Schema，使枚举项只包含当前问题已检索对象；计划提交后，引擎再次独立验证其语义完整性，因为 JSON 格式正确并不代表所有必要语义选择都已完成。

<div class="method-step__io" markdown="1">

**输入**：动态生成的候选枚举项，包括已检索的主体、指标、属性、操作符和路径句柄。<br>
**输出**：经审查并接受的结构化语义计划，包含所选对象、路线、角色约束、过滤条件和输出粒度等编译所需决策。

</div>

**直观理解**：这像一张只能勾选已有选项的表单：模型可以选择，但不能在表单中输入一个目录里不存在的新表名。提交后还要由另一道检查程序确认“该选的都选了、角色没有丢失、路线确实合规”。

</div>

</div>

**优化目标如何起作用**：原文所给方法章节未说明模型训练数据、损失函数、参数更新目标或端到端训练过程，因此不能据此构造训练目标。该系统在所述流程中更像是一个推理时规划与确定性编译系统：规划代理调用检索和审查工具并提交结构化计划，随后由引擎验证和编译；是否对代理进行预训练、微调或其他优化，原文未明确报告。

<details class="paper-details" markdown="1">
<summary>查看关键模块、训练与复现补充</summary>

**关键模块**

**1. 受治理语义模型与物理映射**

该模块由两个作者维护的输入文件组成：语义文件不直接命名表、列或连接谓词，而是定义概念、关系边、角色和指标；物理映射文件负责将这些语义对象绑定到物理数据库结构。关系边的角色是边身份的一部分，而不是对通用遍历附加的普通过滤条件；角色对象自身也可以携带相同的角色谓词。ACME 模型中有 26 条边，其中 9 条带有角色或标记表等语义承诺，另有 3 个角色概念具有绑定谓词；这些承诺不能由规划代理引入或改写。

> 直观理解：该模块把企业规则写成机器可检查的地图。它确保“由代理销售的保单”和“由持有人持有的保单”在地图上就是不同道路，而不是查询时才临时解释。

**2. 绑定解析器与确定性路径枚举器**

解析器接收问题中的原文片段，将其绑定到受治理概念、指标、属性、期间、字面量和目标对象；路径枚举器随后在语义图和物理映射上执行确定性搜索，并受角色、支持范围和跳数上限约束。多跳关系以路径句柄暴露给模型，规划代理只需在候选路线之间选择，不需要合成边序列。数据库探针可以提供字面量落地和观测扇出信息，但不能覆盖治理文件中声明的关系基数。

> 直观理解：解析器解决“问题里的词对应目录中的什么”，路径枚举器解决“从这些对象出发哪些走法合法”。将两者交给确定性程序，可以减少模型因遗漏一步连接或混淆角色而产生的错误。

**3. 受限规划代理与确定性 SQL 编译器**

规划代理是一个多轮代理，只能使用固定类型工作流，并且没有 shell 或 SQL 工具。引擎根据当前检索结果动态构造 submit_plan 的枚举约束，并在提交后独立验证语义完整性；编译器再依据接受的计划输出完整 SQL，负责治理路径、角色谓词、分组、指标聚合和必要的预聚合。语义图将扇出分类按方向声明；ACME 的正向关系包括 12 条 none、13 条 bounded 和 1 条 multiplicative，但编译时 bounded 与 multiplicative 均被视为可能造成行数扩张的关系。

> 直观理解：该模块把模型限制在“选择题”范围内，并把高风险的 SQL 细节交给规则明确的程序。这样既保留模型理解自然语言的能力，也避免让模型直接控制数据库连接和聚合逻辑。

**训练与推理**

推理时，系统首先读取并严格验证语义文件与物理映射文件；验证失败会阻止部分绑定模型进入编译器。面对每个问题，规划代理提交由问题原文片段组成的分解，解析器将其绑定到受治理对象，路径枚举器依据治理约束和跳数上限生成候选路线，数据库探针可辅助字面量落地和扇出诊断。随后引擎动态生成只包含当前候选对象的 submit_plan 枚举约束，代理在多轮中调用检索或审查工具，或提交结构化计划；引擎独立检查计划的语义完整性。计划通过后，确定性编译器依据语义模型和物理映射生成完整 SQL，包括角色谓词、受治理连接、指标聚合、分组及必要的粒度转换。所给章节没有报告训练阶段、训练语料、优化器、推理采样策略或模型参数。

**复现信息**

复现或公平解释该方法时，必须保留语义文件与物理映射文件的分离，因为前者表达业务含义，后者表达数据库实现；同时需要实现加载阶段的八项失败即停止校验，不能把未绑定对象当作可用对象。还需记录每条关系的端点、角色、基数、双向扇出分类及证据，并为角色关系、标记表和角色概念保留其绑定谓词。路径搜索必须是确定性的，并受治理约束、支持范围和跳数上限控制；候选路线应以路径句柄而非可自由改写的边序列提供给代理。最后，submit_plan 的枚举值必须由当前问题的检索结果动态生成，并在提交后执行独立语义校验；数据库观测只能用于字面量和诊断标注，不能改变声明的关系基数或路径可接受性。关于具体数据库系统、代理所用基础模型、八项校验规则的完整清单、跳数上限数值、SQL 方言和运行时配置，原文未明确报告。

<div class="metric-list" markdown="1">

<div class="metric-item" markdown="1">

**问题级稳定成功率（solid success）**

一个问题的3次运行必须全部被接受才算稳定成功。该指标同时惩罚错误和跨运行不稳定，是主要估计量；系统间推断使用同一问题上的两侧精确McNemar检验，Wilson 95%区间只描述各系统自身比例。 （越高越好，因为它要求系统不仅偶尔生成正确SQL，而且在有限的3次重复运行中持续成功。）

</div>
<div class="metric-item" markdown="1">

**至少一次成功率（at-least-once success）**

一个问题的3次运行中只要至少一次被接受即计为成功。它衡量系统是否具备解决该问题的能力，但会掩盖重复运行的不稳定性，因此是稳定成功率的补充指标。 （越高越好，因为更高比例表示系统至少能够在某次尝试中得到可接受答案；但不能单独证明可靠性。）

</div>
<div class="metric-item" markdown="1">

**运行级结果类别**

对每次运行区分成功、拒绝、裁决错误和$\mathrm{agrees\_on\_this\_data\_only}$风险标记。预测SQL与参考SQL先执行；同列宽的行值多重集完全一致时由确定性比较处理，其余未决情况由gpt-4o依据问题、两份SQL和执行结果进行至多3票的多数裁决。 （成功运行越多越好，裁决错误和仅在当前数据上碰巧一致的风险标记越少越好。拒绝通常也计为未成功，但相较于返回可执行却错误的SQL，它能避免静默错误，因此需单独解释。）

**这篇论文还没有解决什么**

- 该实验比较的是两个信息和机制均不同的完整系统：SPC额外获得人工编写的业务本体与物理映射，并使用受限规划、确定性编译、拒绝和一次重试；B0只看到问题与DDL且只调用一次。研究没有组件级消融，也没有控制总模型调用、token和成本，因此无法判断42.1个百分点的差异由哪个组件贡献，或是否值得相应的建模与实现成本。
- 复现和外推范围有限。38题排除注册表是在查看输出后事后建立的，问题并非企业工作负载总体的随机样本；两组温度与端点元数据也未被完整保存。当前归档缺少主实验执行数据库、反事实环境、精确工作树及次要模型逐运行判决文件，因此聚合统计可以审计，但实验不能端到端复现，也不能据此证明跨行业、跨数据库或长期运行稳定性。

<details class="paper-details" markdown="1">
<summary>查看 baseline、实验问题、消融与复现细节</summary>

**主要 baseline**

- B0直接接收自然语言问题和数据库DDL，由语言模型自行决定联接、谓词、聚合及最终SQL。它不使用业务本体、物理映射、确定性编译器或拒绝接口，因此代表常见的端到端DDL-to-SQL方案。B0与SPC使用相同问题并按相同执行与裁决流程评分，因而是主要配对基线；但两者可用信息和执行机制均不同，比较只能估计完整系统差异。
- 严格等价评分不是独立系统基线，而是主评分规则的保守参照：主规则把$\mathrm{equivalent}$和$\mathrm{superset}$均计为成功，严格规则只接受$\mathrm{equivalent}$。它用于判断主要结论是否依赖“多投影列但答案仍包含正确内容也算成功”这一有争议的裁决。
- 44项全集统计是分母敏感性参照，而非干净的性能基线。它保留6个被主要分析排除的问题，并把B0未运行的方言不兼容问题按失败计入，从而显示事后排除规则对结果的影响；但该统计混合了模型错误、参考语义缺陷和SQLite移植问题。

**实验想回答的问题**

- 在同一组企业保险问题上，完整的SPC系统，即“受限语义规划加确定性编译”，是否比直接根据问题和数据库DDL生成SQL的B0系统具有更高且更稳定的端到端正确率？该比较针对完整系统效果，因为SPC同时增加了业务语义信息、受限规划接口、确定性编译、拒绝机制和一次重试策略，不能据此单独归因于某个组件。
- SPC的优势是否对评分口径、评测分母、规划模型选择和关系多重性变化保持稳健？其中，反事实多重性测试专门考察“粒度不安全”SQL：这类SQL可能在原始数据库上碰巧与参考答案一致，但在不改变目标业务事实、只增加无关联接扇出或角色记录时产生重复计数。

**实验实现**

主要比较采用gpt-5.6-luna，每个问题运行3次，因此38个问题对应每个系统114个报告结果。B0每次只进行一次直接生成且不能拒绝；SPC若被确定性流程拒绝，可额外进行至多一次新规划。114个SPC结果中有10次触发重试，9次最终生成SQL、1次仍拒绝，共消耗124次规划尝试；一次规划尝试还可能包含多轮模型交互。研究没有测量两组的模型调用数、token或成本是否相等。两组脚本都请求温度$0.0$，但B0的服务商拒绝该参数并实际采用默认值，SPC汇总工件又没有保存最终传输温度和端点，因此作者不主张采样参数已严格对齐。另以gpt-5.4和gemini-3.6-flash运行同一SPC流程作为模型敏感性看板，但没有对应的B0结果，不能纳入配对假设检验。裁决规则被冻结后，从保存的判决工件重新生成主要及敏感性统计；不过原始执行数据库、反事实环境、主实验精确工作树以及次要模型的逐运行判决文件并未完整归档。
